## 二、新增机制（一）

### 1.1　在途感知选号　🆕

**问题**：池子原有的三层偏好 —— 手动权重、临期积分、剩余用量 —— **全是静态属性**。
静态偏好之下，并发请求会自发收敛到同一个账号上。
而 `wb_proxy` 自己的注释就写着后果：上游按「账号 + 分钟」计 token，
两个会话落在同一账号上很容易冲破配额然后 429，换号又因为丢了前缀缓存而更慢
（TTFT 1.5s → 5~6s）。

**做法**：

1. 新增 `wb_proxy._ACCOUNT_LOAD` —— **永远打开**的在途计数器。
   （与「每账号并发上限」开关**无关**：那个开关默认 0 = 不限，不记账 ——
   默认配置下池子本来看不到任何负载信号。）
2. `AccountPool.set_inflight_provider()` —— 注入式只读取值。
   **避免 `wb_accounts` 反向 import `wb_proxy` 成环。**
3. 选号时按在途数分组，最闲的那组胜出；组内仍按权重轮转。
4. 权重是「同等条件下先给谁」的偏好，不是「独占」：
   带权重的账号比池里最闲的账号还忙时，让路给闲的。

**效果**：这是**预防侧**；原有的「每账号并发名额」是反应侧（撞到上限才换号）。
两者互补。

**借鉴来源**：Coding2API `src/engine/scheduler.py:300-308`。

### 1.2　半开探测　🆕

**问题**：冷却一到期，**所有**并发请求会同时压到刚解冻的同一个账号上，
形成「冷却 60s → 到期 → 全员压上 → 再撞 → 再冷却」的锯齿。

**做法**：冷却到期后账号进入半开态，只有**一个**在途请求被放去试探；
其余请求改选别的账号。试探成功 ⇒ 标记为已恢复（TTL 120s）。

**关键语义（两次返工才做对）**：

- 半开**不是优先级，是资格** —— 有健康账号就用健康的，半开的让路；
  全都半开时才放一个出去。
  （第一版做成「只要有半开账号就选它」，结果刚解冻的号**独占**所有请求 ——
  正好是半开探测要避免的那种「压上一个号」。）
- 冷却到期时刻必须在 `ready()` 过滤**之前**记录 —— 冷却中的账号根本过不了
  `ready()`，在可服务账号上记录的话那段代码永远走不到（功能等于死代码）。

**借鉴来源**：Coding2API `src/engine/half_open.py:41-101`。

### 1.3　上游错误分类　🆕

**问题**：同一句「请求失败」对账号的含义并不一样，但旧实现一视同仁地冷却。
最要命的是 **401**：刷新失败后无条件记 60 秒冷却 ——
但「刷新因为网络抖动没成」与「上游明确判这个凭据失效」是完全不同的两件事。
把它们一视同仁地惩罚，代价是救火的时候一次上游抖动就摘掉一批号，池子容量骤降。

**做法**：五类判定 ——

| 分类 | 含义 | 处理 |
|---|---|---|
| `ERR_CREDENTIAL` | 凭据被拒（403/11140、401 刷新失败且凭据判死、402） | 冷却 |
| `ERR_MODEL` | 模型/额度维度（429、6004、14003） | 只记模型冷却，账号不背锅 |
| `ERR_REQUEST` | 请求本身的问题（400/404/422…） | 只记录，不冷却 |
| `ERR_TRANSIENT` | 排队/瞬时（5xx、连接异常） | 只记录 |
| `ERR_LOCAL_NETWORK` | 本机网络不可用 | 只记录 |

**判定顺序有意义**：业务 code 优先于 HTTP 状态码 ——
403+11140 是凭据类（账号级风控），429+14003 是模型类（被限流），
两者 HTTP 状态相同但含义相反。

**code 提取只认 JSON 正文里的 `code` 字段** —— 正文里出现「11140」这几个字符
不等于 code 是 11140。

**借鉴来源**：Coding2API `src/provider/base.py:30-71`。

### 1.4　上游恢复时刻双侧夹取　🆕

**问题**：上游正文里的重置墙钟是**上游的事实**，但可能不可信 ——
已经过去（时钟偏移）⇒ 冷却 0 秒，账号立刻重新上线然后立刻再撞；
荒唐地远（「下个月恢复」）⇒ 账号被停放一个月，等于从池子里静默消失。

**做法**：`RATE_LIMIT_RESET_MAX_WAIT = 24 小时` 夹上界，
下界沿用原有的 1 秒。夹取后 `reset_at` 同步改写，
让窗口探针与面板显示的恢复时刻一致。

**借鉴来源**：Coding2API `src/engine/scheduler.py:129-152`。

### 1.5　金丝雀 SSE 固件　🆕

**问题**：协议回归全是函数级断言，`tests/` 下**没有任何 golden 快照文件**。
v0.1.1（参数被网关吃掉）与 v0.1.2（函数名被拼成串）两次线上事故，
都是靠「真实上游帧的固定样本」才复现的 —— 但样本只存在于那条测试文件的代码里，
换个测试文件就没有了，别的协议路径想用同一份样本得复制粘贴。

**做法**：新增 `tests/fixtures/upstream_sse/`（6 份固件）：

| 固件 | 内容 | 守住什么 |
|---|---|---|
| `chat-basic.sse` | 普通流式回复 | 正文不被误删 |
| `tool-calls.sse` | 单工具调用（12 帧，实测抓取） | **参数完整 + 函数名只出现一次** |
| `tool-calls-parallel.sse` | 三个并行调用（20 帧） | 并行不串名 |
| `error-11140.body.json` | 账号级风控正文 | 11140 优先于 401/403 判定 |
| `error-14003.body.json` | 软限流正文 | 429+14003 ⇒ 凭据被接受 |
| `error-6004.body.json` | 额度封禁正文 | 恢复时刻可解析 |

配 `tests/_make_sse_fixtures.py`（生成脚本）与 `tests/_test_sse_fixtures.py`（13 项），
后者分两层：**回放**（固件喂给网关清洗逻辑）+ **守门**（固件本身的形状，
有人手改固件来「让测试过」会被拦住）。

**借鉴来源**：Coding2API `src/provider/fixtures/{codebuddy,trae}/*.sse`。

## 三、新增机制（二）：安全加固

| # | 项 | 说明 |
|---|---|---|
| 1 | **`settings.json` 损坏 ⇒ fail closed** | 面板登录与鉴权判定见到损坏标记就拒绝；`save()` 拒绝用空内容覆盖坏文件；坏文件留档成 `.corrupt` |
| 2 | **凭据不落盘、不进日志** | 上游错误正文里的 bearer token 落盘前脱敏（与活动历史同一套规则）；`usage.jsonl` 权限 0600、目录 0700 |
| 3 | **登录限速不可被 XFF 绕过** | 取 XFF **最右**（代理追加的那一段），客户端改不动 |
| 4 | **面板口令不出现在地址栏** | `?pwd=` 读到即从 URL 删除 |
| 5 | **告警 SSRF 解析失败 ⇒ 拒绝** | 与 `wb_webtools` 的策略统一成 fail closed |
| 6 | **危险 webhook URL 落不了盘** | `set_alerts()` 增加 URL 合法性校验 |
| 7 | **更新包有体积上限** | 下载 128MB / 解压总量 256MB / 文件数 1200（与 systemd 更新器对齐） |
| 8 | **特权执行器不听请求文件的** | 更新目标目录改用执行器自己的 `--root`；读请求加 `O_NOFOLLOW` |
| 9 | **异常不再变成连接重置** | 处理函数抛异常 ⇒ 返回正经的 500，账本记得到，栈照样打 |

## 八、从 v0.1.7 升级需要注意的

1. **compose 的 image 行要手工改**（CI 不管它）。
2. **`settings.json` 损坏 ⇒ 网关会拒绝启动时的面板登录**（这是有意的 fail closed）。
   如果你的部署正好有坏掉的配置，第一次启动会看到面板登不上 ——
   那是保护生效，不是故障。坏文件会被留档成 `accounts/settings.json.corrupt`。
3. **面板口令请在 `.env` 里设成随机强口令**（默认 `admin` 是既有设计，本版未改）。
4. **启动脚本建议设 `TZ`**：本项目有三处「日界」语义不同（宿主机本地时区 / 固定 +08:00 / UTC），
   compose 与 Dockerfile 已经设了，裸机启动脚本没有。
5. **`?pwd=` 现在会被从地址栏清掉** —— 之前用它自动登录的脚本不受影响（口令仍在参数里被读取），
   只是地址栏不再留痕。
