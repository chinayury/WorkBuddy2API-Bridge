## 三、为什么是「三方合并」而不是「切到 v1.9.2 基线」

本项目 `master` 与上游**没有共同祖先**（v0.1.0 基线是从已验证发布包还原的，
重新起了提交历史）。因此不能 `git merge upstream/main`，只能：

1. 以 `d1a8913` 为 base 做**三方合并**（`git merge-file --diff3`），逐文件判定；
2. 冲突逐处人工裁决，而不是自动取一侧；
3. 回归跑满 249 个套件。

三方合并的冲突面：**4 个文件 / 15 处**（README 4、wb_proxy 8、wb_accounts 2、Makefile 1）。

### 4.1 唯一的语义级冲突：`ready(refresh=False)` 到底算不算「可用」

- **上游**：只读口径下「快到期」**仍算可用**，只是不发起刷新。
- **本项目原实现**：只读口径下「快到期」直接判**不可用**。

并入上游后，上游新增的 `tests/_test_health_readiness.py` 两条用例红。
逐行看过之后判定**上游是对的，本项目原实现是过度纠正**，原因是本项目自己
已经写好了配套的另一半：

- 选号路径用 `refresh=False` 扫池（**不**产生网络请求）；
- 真正要用这个账号的那一步（`wb_proxy.open_upstream`）用
  `account.token_needs_refresh()` 给**选中的那一个**账号刷一次，刷新失败就换号。

本项目原实现把临期账号在选号阶段就剔掉，等于**把刷新这条路整个堵死**：
池里所有账号都临期时网关会报「无可用账号」(503)，而这些号其实每个都能
刷新后正常服务。改成上游语义后：

- 刷新仍然是「按需、只刷被选中的那一个」，不会退化成刷新风暴；
- `/health` 的按模型可用数（#667）不再少算临期账号。

### 4.2 上游的统一失败出口改用本项目的判据

上游 #666 把池空失败的「状态码决定 → 落账 → 回客户端」收成一个出口
（`upstream_failure_response`）。本项目的 ops 补丁早就做过同一件事，但多认了
一条措辞（`no healthy account`，`gateway_hint` 用的），而且只覆盖三条协议里的两条。

裁决：**采用上游的出口，但让出口调用本项目的 `_empty_pool_status()`**，
于是「状态码只有一个决定点」和「三条协议同一判据」两个意图同时成立。

## 五、顺带修掉的两个本项目自己的问题

1. **基线里的 10 处乱码**：`wb_accounts.py` / `wb_proxy.py` / `wb_alerts.py` /
   `wb_update_external.py` 的中文注释里有 U+FFFD 替换字符（v0.1.0 基线从发布包
   还原时经过一次 GBK 往返）。上游 `d1a8913` 为 0，说明是本项目自带的。
   已按上下文逐处补回正确汉字，仓库现已 0 处乱码。
2. **`count_ready()` 收了 `refresh` 参数却不用**（见上表），并入上游实现后修复。

## 六、下次跟版的做法（沿用本次流程）

1. `git fetch upstream --tags`，看 `refs/tags/*` 与 `upstream/main` 的差集；
2. 算出「上游相对基线」与「本项目相对基线」两份 diff，交集即冲突面；
3. 三方合并（base = 上游基线提交），冲突逐处人工裁决，**不自动取一侧**；
4. 跑满套件 + `scripts/check_clean_checkout.py`；
5. 更新 `docs/CHANGELOG.md`（上游的）+ 本项目自己的 `docs/CHANGELOG-v0.x.y.md`；
6. 版本号三处一致：`VERSION` / `wb_proxy.py` 两处 / `wrt/.../Makefile`；
7. README 的**套件数是数字型断言**，合并后必须按目录重算，否则
   `tests/_test_release_engineering.py` 会红。
