### 二、改动 1：区域暂停持久化（移植自 ops 补丁）

**问题**：区域暂停（整池 30 分钟）原先**只在内存里**（`_RESTRICTION_HOLD`）。
容器一重启 —— 升级、崩溃、被 OOM kill —— 30 分钟的暂停就没了。

**为什么这很要命**：上游刚把这一区域的账号判非法（403 11140）这个事实被丢掉，
池子立刻恢复派发 → 冷账号重新上桌 → 再吃一次 11140 → 900 秒内凑够两次
→ 触发**第二轮**整池连坐。

**这不是假想**。2026-10-26 晚生产上的连坐在容器内 **15:33~15:35 连续触发 7 次**，
涉及 `f7102b2e` —— 正是 10-27 凌晨被拆掉的那颗炸弹。**同一晚我们部署 v0.1.4
重启了容器**。那 7 次连坐里只要有任何一次跨过重启点，事故就会重演。
⇒ 这条不是「加固」，是**修复同一条链上的第二段**。

**落点**（`wb_proxy.py`，约 150 行）：

| 元素 | 作用 |
|---|---|
| `_load_restriction_state_locked()` | 读 `usage/restriction-state.json`，恢复**原始到期时刻**（不重置） |
| `_save_restriction_state_locked()` | 原子写：tmp + `O_EXCL 0600` + `fsync` + `os.replace` |
| `restriction_state_snapshot()` | 只读快照，挂到 `/health` |
| `note_account_restriction()` | 事件 key 由**明文 uid** 改为 `sha256(uid)`；写盘 |
| `reset_restriction_state()` | 清内存**并把空状态落盘**（否则「已清空」重启后又回来） |
| `restriction_hold_remaining()` | 加显式关闭语义：`WB_RESTRICTION_HOLD_SECONDS=0` 永远不暂停，重启后依然 |

**边界与安全**：
- 落盘只含**元数据**（账号哈希、事件时刻、原始到期），**不含任何令牌**；
- 拒符号链接（读侧写侧各一次）、1 MiB 上限、每区域 4096 事件上限；
- **坏文件只记诊断，不发明暂停** —— 宁可少暂停，不可凭空停池；
- **写失败不得丢掉内存里的暂停**（那正是我们要防的事），只计数 + WARN。

**落地前提已核实**：243 上 `usage/` 是**持久卷**（compose 里 `./usage:/app/usage`），
状态文件能跨重启存活 —— 不是白做。

**刻意保留的两处我方优势**（没有照抄补丁）：
1. **「暂停生效期间不续期」** —— 补丁那行 `max(held, now+HOLD)` 会让面板的
   「测试账号」按钮每次探测都把暂停往后推 30 分钟，池子就一直红着。
2. **`wb_alerts` 的连坐告警** —— 补丁没有主动通知，我们有。

### 三、改动 2：空池三协议统一 503（真 bug）

**问题**：三条协议在「池子里没有可用账号」时给的码**不一致**：

| 路径 | 原判据 | 原结果 |
|---|---|---|
| Chat | `message.startswith("no usable account")` | 503 ✓ |
| Responses | 同上 | 503 ✓ |
| **Anthropic Messages** | `"no account" in low or "no enabled account" in low` | **502** ✗ |

而真正抛出的消息是 `"no usable account for realm '...'"` ——
子串 `"no account"` **不出现**在 `"no usable account"` 里（中间隔着 `"usable "`），
所以 Anthropic 路径的空池落到了 502。

503 与 502 给客户端的处置动作**完全相反**：
* 503 = 网关这边没账号可用了 → 运营者去加号/启用；
* 502 = 上游挂了 → 客户端重试可能有用。

**还发现第二个问题**：Chat/Responses 路径**账本记 502、响应给 503** ——
同一个事件在两处口径相反，排查时看到的是「账本说上游挂了、客户端说缺账号」。

**修法**：抽成共享的 `_empty_pool_status()`，三处共用；账本与响应用同一个码。

### 四、改动 3：`11140` 的 code 匹配收紧右边界（真 bug，后果严重）

**问题**：原正则 `r'"code"\s*:\s*"?11140"?'` **没有右边界** ——
`{"code":111400}`（另一个 code）也会被判成账号级风控。

**误判的代价**：冷却一个**健康账号** + 把它记进连坐事件（900 秒内 2 次即触发
整池 30 分钟暂停）。也就是说，一个上游的配额类 code 能引发整池故障。

实测对比：

| body | 应为 | 修正前 | 修正后 |
|---|---|---|---|
| `{"code":11140,...}` | True | True | True |
| `{"code":"11140"}` | True | True | True |
| `{"code":111400,"msg":"rate limited"}` | False | **True** ✗ | False ✓ |
| `{"code":111401}` | False | **True** ✗ | False ✓ |

**顺带确认了一件事**：措辞标记（`unusual activity` / `账号存在异常行为` / `已被限制`）
**必须**在 403 语境里才生效 —— 429 / 6004 的正文里也可能出现「已被限制调用频率」。

### 五、改动 4：网页活跃（daily-chat）不碰未验证账号

审计指出的一条**事故链帮凶**：网页活跃是**唯一会主动向上游发请求**的路径。
v0.1.4 的护栏挡住了**模型请求**路径上的派发，但这条独立链路护栏管不到 ——
冷账号会被 daily-chat 主动探出 403 11140，而当时 `wb_accounts.py` 的
HTTPError 分支只把它变成一个错误字符串（不冷却、不隔离、不计连坐）。

**改法**：`wb_scheduler.py` 选 daily-chat 目标时加 `is_unverified()` 闸门 ——
未通过上游验证的账号直接跳过（并记一行日志说明为什么跳过）。

### 六、顺带修掉的一个既有 flaky test

`_test_daily_chat_web_retry_backoff.py::test_upstream_500_is_a_create_phase_failure`
**本身偶发失败**（5 次跑里红 1 次）。根因：它断言错误正文里含 `'14220'`，
但这条用例会**真的发 HTTP 请求**，Windows 上连接偶尔被网络栈截断
（`WinError 10054`），此时正文里就没有 14220 了。

失败仍然是 `create` 阶段（发请求本身就在 create 阶段）—— 用例要验的正是这个分类。
⇒ 改为断言 `phase` / `attempts` / `error` 非空，**不再断言错误文本内容**。
这让测试不再依赖网络状态。
