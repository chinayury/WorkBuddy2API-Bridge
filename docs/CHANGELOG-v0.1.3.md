### 1. 上游 #644：stderr 日志通道不再阻塞请求线程

`log()` 原先在请求线程里直接 `sys.stderr.write()` + `flush()`。已有的 `try/except`
接得住「写抛异常」，接不住「写阻塞」——stderr 是一条读端还在却没人消费的管道时
（后台任务、服务管理器、`| tee` 消费端已退出、agent runner 拉了 `stderr=PIPE` 却不读），
缓冲写满后 `write()` 永久不返回且**不抛异常**。

`send_response()` 会先调 `log_request()`，于是每个请求都停在**响应头发出之前**；
`/health`、`/realm`、`/panel/status` 在静默白名单里照常 200 —— 从外面看就是
「服务健在、只有面板坏了」，实际请求线程全停在 `log()`。

上游改成：请求线程只对有界队列（2000 行）做 `put_nowait()`，真正的写由一个
守护线程独占；它阻塞也只阻塞它自己。队列满则丢行并计数（首次与每 1000 行把
「正在丢日志」以 WARN 记进看板日志，不再往堵住的通道上写）。退出路径
（`/shutdown` 与控制台关闭处理）用 0.5s 超时把已入队的行刷完，卡住的通道拖不住退出。

**与本项目的合并点**（唯一冲突，`wb_proxy.py` 的 `log()`）：

| 侧 | 写法 |
|---|---|
| 上游 | `line = f"... {_mask_text(str(msg))}\n"` → `_LOG_QUEUE.put_nowait(line)` |
| 本项目 v0.1.0 起 | 同步 `sys.stderr.write(f"... {_mask_text(_mask_secrets(str(msg)))}\n")` |

解法：**取上游的异步队列写法，保留本项目的 `_mask_secrets` 凭据打码**。
两者都要 —— 前者保证写 stderr 卡住时不阻塞请求线程，后者保证日志里不漏
已登记的运行时凭据（账号 token、面板 API Key）。上游没有 `_mask_secrets`，
本项目没有异步队列，缺任何一边都会在对应场景出问题。

`log()` 之外的其余改动（`atexit` 注册、`flush_log_channel`、后台写线程）干净应用。

### 2. 上游 #647：国际版沙箱证书失败时降级到活跃上报

上游给网页通道分配的 ACP 沙箱域名 `*.workbuddy.cloudagent-app.net` 解析到腾讯云
EdgeOne，边缘节点下发的是 `*.cdn.myqcloud.com` 通配证书，Python 的 ssl 必然报
`Hostname mismatch` —— 这一轮重试永远不会成功。旧实现却把它当成「这一轮没跑完」
按预算重试到底，最后整轮判 `ok: false`，面板上一片「集体封号」的错觉
（实际积分照发，丢的只是连登）。

改动：

1. **国际版也能上报活跃**：`report_activity()` 不再只限国内版，国际版按自己的 base
   （`www.workbuddy.ai`）打 `POST /v2/report`；
2. **streak 端点跟随出口**：`fetch_streak_days()` 按账号出口选 base，连登天数正确回显；
3. **证书失败降级**：网页腿失败且错误串命中证书校验标记时，若设置页新开关
   「证书失败改走活跃上报」打开（**默认关**），改走一次活跃上报并把当天算完成
   （结果带 `web_fallback` 明细）；**开关关着时行为与升级前完全一致** —— 仍如实报失败、
   仍不写 `lastDailyChat`，好让下一轮巡检重试；
4. **非证书类失败一律不降级**（沙箱没就绪、轮次超时、业务拒绝），避免把
   「真的没跑完」记成完成。

新增 `tests/_test_daily_chat_activity_fallback.py`（12 项），
`tests/_test_streak_report.py` 里两条「国际版永不参与活跃上报」的断言按新语义改写。

### 部署后的一次上游风控事件（非本版引入）

部署验收时打了 4 个模型的流式工具调用，触发了**上游 403 / code 11140**（账号级风控），
进而触发**连坐保护**（同区域 900s 内 ≥2 个账号被限制 → 整池暂停派发 1800s），
客户端在一段时间内统一拿到 429。

**这是账号池的既有模式，不是 v0.1.3 引入的**：

- 被限制的两个账号 `31ab6921` / `3cfa1fab` 在 `usage.jsonl` 里**从未成功服务过**
  （只有 403/429 记录，无一次 completed）—— 属于「冷账号」，是 11140 的已知高危目标；
- 池内共 **9 个冷账号**（从未成功服务过），巡检已列为 WARN；
- 另有账号在**本次部署之前**（约 16:21）就已被 11140 限制过，冷却到 17:21 ——
  说明 11140 在本部署上一直在发生；
- v0.1.2 与 v0.1.3 的风控相关代码**完全一致**（连坐/11140 符号命中数两边都是 6），
  本版只改了日志通道与国际版活跃上报，不碰派发与风控逻辑。

**处置**：连坐暂停期**不自动续期**（代码里显式 `max(held_until, ...)` 冻结），
到点自动恢复；两个受限账号冷却 7200s（2 小时）后回池。巡检脚本已补上
「账号级 11140 冷却中 N 个，最早恢复 HH:MM:SS」与「受限账号里有冷账号，建议停用」
两条判据 —— 用户看到 429 时能直接知道要等到几点。

> **建议**（需用户决定，本次未自动执行）：停用那 9 个从未成功服务过的冷账号。
> 它们每次被派发都可能触发一次 11140，而 900s 内 2 次即触发整池 30 分钟连坐暂停。
