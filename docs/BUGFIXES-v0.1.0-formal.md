## 一、安全类

### S-1　`settings.json` 损坏 ⇒ 网关 fail-open（CRITICAL）

- **现象**：`settings.json` 存在但解析不了时，面板密码回落成默认的 `admin`，
  同时 API Key 列表读成空 ⇒ `auth_required()` 判定「不需要鉴权」
  ⇒ `/v1/chat/completions` 对所有能碰到端口的人开放，消耗上游账号额度。
  每日限额/积分限额也一并回落到默认值。
- **触发**：手改坏、从半截备份恢复、卷重挂。`wb_atomic` 的原子写让自伤很难发生，
  但外部损坏完全可能。
- **根因**：`wb_settings.load()` 的 `except Exception: pass` 让「文件不存在」
  与「文件存在但坏了」变成同一件事（都返回空 dict）。
- **修法**：
  1. 加载失败时打上 `_UNREADABLE` 标记（`wb_settings.py`）；
  2. `verify_panel_password()` / `panel_password_is_default()` 见到标记就**拒绝**
     （fail closed）—— `admin` 在损坏状态下**开不了面板**；
  3. `wb_proxy.auth_required()` 见到标记就**要求鉴权**（而不是「没配 Key ⇒ 不用鉴权」）；
  4. `wb_settings.save()` 拒绝用带标记的内容覆盖原文件，
     并提供 `quarantine_unreadable()` 把坏文件留档成 `.corrupt`（不删、不改）。
- **回归网**：`tests/_test_settings_fail_closed.py`（16 项）。

### S-2　上游错误正文里的凭据被原样落盘（HIGH）

- **现象**：上游 401/403 的正文**会回显授权头**（`wb_activity.safe_message`
  的注释里就写着这件事）。那行正文原样进 `usage/usage.jsonl`，
  **也原样进运行日志**（日志又进面板的「运行日志」页）。
- **触发**：任何一次上游 401/403。
- **根因**：`record_error()` 用 `str(message)[:200]`，既没过脱敏，
  也没给 `usage.jsonl` 设权限（默认 0644，同机任何用户可读）。
- **修法**：
  - 落盘与日志都改走 `wb_activity.safe_message()`（与活动历史**同一套**脱敏规则，
    避免两处规则漂移出新的漏洞）；
  - `usage.jsonl` 权限收紧到 0600、`usage/` 目录 0700（与凭据文件同一把锁）。
- **回归网**：`tests/_test_security_v010.py`（15 项，含「日志行也脱敏」）。

### S-3　登录限速被 `X-Forwarded-For` 绕过（HIGH）

- **现象**：5 次/60 秒的面板登录限速形同虚设 —— 每次请求换一个伪造的
  `X-Forwarded-For` 左半段，就换一个限流桶。
- **触发**：任何能访问端口的人；本机任意非特权进程也能（回环对端被当成可信）。
- **根因**：`login_rate_limit_key()` 取 XFF 的**最左**一段。
  而 nginx 的 `$proxy_add_x_forwarded_for` 是**追加**：客户端自带的值留在最左，
  代理把真实来源追加到最右 ⇒ 最左是**客户端自己写的**。
- **修法**：改为从右往左找第一个能解析的段（那是代理追加的、客户端改不动的）。
  `X-Real-IP` 仍然优先。
- **回归网**：`tests/_test_login_ratelimit_proxy.py` 里两条用例改为断言新语义，
  并新增一条「伪造不同的左半段仍是同一个桶」。

### S-4　面板口令 `?pwd=` 留在地址栏（HIGH）

- **现象**：用 `?pwd=` 自动登录后，口令**留在地址栏** ⇒ 进浏览器历史、
  同步到别的设备、出现在屏幕共享里，还会作为 `Referer` 发给站外资源。
- **根因**：清理 URL 的代码只删了 `key`，没删 `pwd`。
- **修法**：读到 `pwd` 后**立刻** `history.replaceState` 把它删掉
  （与 `?key=` 同款处理，只删这一个参数，保留 `?tab=` 等）。
- **回归网**：`tests/_test_security_v010.py`（断言删除动作存在，且发生在登录提交**之前**）。

### S-5　告警通道的 SSRF 防护在 DNS 解析失败时 fail-open（HIGH）

- **现象**：域名第一次解析失败、第二次解析到 `127.0.0.1` ⇒ 校验通过、连接打内网。
- **根因**：`wb_alerts._is_internal_host()` 解析失败时 `return False`（不阻断），
  而且校验与连接是**两次独立的解析**（TOCTOU）。
- **修法**：解析失败一律**拒绝**（fail closed）—— 收不到告警比被 SSRF 打穿好得多。
  同仓库的 `wb_webtools._guard_url` 本来就是 fail closed 的，现在两处策略一致。
- **附带**：`wb_settings.set_alerts()` 补上 URL 合法性校验（延迟 import 避开循环依赖），
  危险 URL 落不了盘 —— 以前能存进配置（投递时被挡），造成「面板保存成功但告警发不出去」
  的长期错位。

### S-6　便携更新路径没有体积/文件数限制（HIGH）

- **现象**：`wb_update_portable.download()` 读到 EOF、`safe_extract()` 逐条写出，
  **无任何上限** ⇒ 一个几百 KB 的 zip 可以解压出几十 GB（zip bomb），
  把磁盘写满。这条路径在 Docker 部署里以 **root** 运行。
- **根因**：systemd 那条更新路径早就有这三道限制
  （`ops/aliyun/workbuddy2api-hub-updater.py:54-58`），便携路径当时漏了。
- **修法**：把 `ARCHIVE_LIMIT=128MB` / `UNPACKED_LIMIT=256MB` / `FILE_LIMIT=1200`
  搬过来，分别用于「下载体积」「解压总量」「文件数量」。
  **解压总量**才是 zip bomb 的正解 —— 限单文件挡不住它。

### S-7　特权更新执行器采信请求文件里的路径（MEDIUM）

- **现象**：`wb_update_external` 跑在特权侧，却按**请求文件**里的 `root` 决定写哪里。
  请求文件是无特权网关写的 ⇒ 低权限方能决定特权进程的写入目标。
- **修法**：`root` 改用执行器自己的 `--root` 配置；
  `read_request()` 补上 `O_NOFOLLOW`（请求目录按设计是组可写的，
  符号链接本该被挡住）。
- **回归网**：`tests/_test_portable_update.py` 新增一条「请求文件不能决定更新落在哪」。

## 二、派发与并发类

### D-1　半开探测是死代码（CRITICAL，**我方自己引入的**）

- **现象**：冷却到期后，半开探测**从未被触发** —— 整个功能等于没做，
  「冷却到期 → 全员压上 → 再撞 → 再冷却」的锯齿照旧。
- **根因**：`_recovery_deadlines`（记录冷却到期时刻）只在
  `_is_freshly_recovered()` 的 `wait > 0` 分支里写，
  而那个函数**只对已经通过 `ready()` 的账号调用** ——
  冷却中的账号根本过不了 `ready()`。
  ⇒ 那段记录代码永远走不到。
- **实测证据**：审计给出的论断经我独立复现：
  `pick` 5 次后 `_recovery_deadlines = {}`、`half_open_probe` 调用次数 **0**。
- **修法**：把「记录到期时刻」挪到 `ready()` 过滤**之前**；
  冷却刚到期的账号作为**半开候选**进入考量。
- **回归网**：`tests/_test_half_open.py`（16 项）。

### D-2　「已恢复」标记的键对不上（HIGH，**我方自己引入的**）

- **现象**：`note_success` 按真实模型名写入恢复标记，
  而查询时用 `model=None` ⇒ 查不到 ⇒ 那个逃生口形同虚设。
- **实测证据**：`_half_open` 的键是 `('uid-b','gpt-4o')`，
  `half_open_is_recovered(None)` 返回 **False**。
- **修法**：`model` 贯穿 `_is_freshly_recovered()` → `half_open_is_recovered(model)`。

### D-3　恢复 TTL 过期时会发出两个试探令牌（HIGH，**我方自己引入的**）

- **现象**：TTL 过期后第一个请求 pop 掉状态并返回 True，**没有重新架起「进行中」标记**；
  第二个请求看到「无状态」→ 自己架一个 → 也拿到令牌。
- **实测证据**：TTL 过期后连续两次 `half_open_probe` 都返回 True。
- **修法**：TTL 分支里改成 `self._half_open[key] = (now, False)` 再返回。

### D-4　手动权重让在途感知完全失效（HIGH，**我方自己引入的**）

- **现象**：池里只要有**一个**账号被手动加权 >1，选号就永远选它 ——
  即使它正背着 99 个在途请求，而别的账号是闲的。
  而这恰恰是「并发请求全压在一个号上」的场景。
- **实测证据**：带权重账号负载 99、另两个为 0 ⇒ 连续 3 次 pick 全选带权重的那个。
- **修法**：权重是「同等条件下先给谁」的偏好，不是「独占」。
  带权重的账号比池里最闲的账号还忙时，让路给闲的；
  负载相同时权重仍然优先（用户设置的意图不被推翻）。

### D-5　一次派发触发 N 次令牌刷新（HIGH，**我方自己引入的**）

- **现象**：旧选号器扫到**第一个**可用账号就停，最多刷新一次；
  改成「先收集全部候选」后，`ready()` 的刷新副作用被放大 ——
  19 个临期账号 = 19 次串行网络刷新（每次最长 30 秒）**全在派发路径上**。
- **实测证据**：3 个临期账号 ⇒ 一次 `pick()` 触发 **3** 次 refresh。
- **修法**：
  1. `ready(model, refresh=False)` —— 选号路径只看「能不能用」，不发起网络请求；
  2. 刷新挪到**选中之后**：新增 `Account.token_needs_refresh()`，
     `wb_proxy.open_upstream` 拿到账号后、构造请求前刷新一次，失败就换号。

### D-6　负载计数的归还回调读了一个会被置空的变量（HIGH，**我方自己引入的**）

- **现象**：归还挂在响应的 `close()` 钩子上，但绑定之后本地标记立刻被置空
  ⇒ 回调执行时读到 `None` ⇒ **归还变成空操作，计数只增不减**。
- **后果比名额泄漏更隐蔽**：名额有上限可见；负载计数没有 ⇒
  那个账号的「忙」值永久虚高 ⇒ 被选号永久排到最后 ⇒ **被静默踢出池子**。
- **实测证据**：旧写法下 close 之后计数停在 1（应归 0）。
- **修法**：闭包**抓住账号本身**（`lambda: account_load_release(acct.uid)`），
  不去读那个随后会被置空的变量。
- **回归网**：`tests/_test_account_load_counter.py`（9 项）。

### D-7　请求构造阶段抛异常会泄漏两个计数器（HIGH）

- **现象**：构造请求的那段（缓存键注入 → 压缩 → 造头 → 建 Request）原本在 `try` 之外，
  任何一个函数抛异常（磁盘满时读文件失败、gzip 失败…）都会直接冲出 `open_upstream`
  ⇒ 循环外的统一归还走不到 ⇒ 名额与负载计数双双泄漏。
- **修法**：那段整体包进 `try`，异常时归还两个计数器并换号。

### D-8　`resp` 在绑定 close 钩子之前可能泄漏（HIGH）

- **现象**：`urlopen` 成功之后、`bind_account_slot_to_response` 之前，
  `account.note_success()` / `wb_egress.note_success()` / `reset_switch_counter()`
  任一抛异常，`resp` 就没人关了 —— 开了连接池时泄漏的是一条复用的 TCP/TLS 连接。
- **修法**：那段整体包 `try/except`，异常时 `resp.close()` 再抛。

### D-9　异常逃到 socket handler ⇒ 连接重置而非 500（HIGH）

- **现象**：处理函数里的异常一路冒到标准库的 `handle_error()` ⇒
  客户端看到的是**连接被重置**，既没有 HTTP 状态码也没有错误正文，
  用量账本里也不留这一笔，运维只看到一段栈。
- **修法**：`do_GET` / `do_POST` 的分发包一层 `try/except` ⇒ 返回正经的 500，
  栈照样打（要排查时看得到），账本也记得到。

## 三、任务自动化类

### T-1　进度轮询只等 3.0 秒 ⇒ 一半任务当天领不到奖（HIGH）

- **现象**：任务上报事件后要等上游把进度落账才能领奖。
  旧写法 `for attempt in range(6)` 看着像等 6 次，但它在 `attempt == 2` 时就 break
  ⇒ **实际只等 3.0 秒**。
- **触发**：落账慢于 3 秒的任务。而这个文件自己记着实测：
  「RichMeow 0/1→1/1 约 3 秒，**Library_read 4 秒**」⇒ 正好有一半任务落在窗口外。
- **后果**：进度没赶上 ⇒ 领奖顺延到**明天** ⇒ 一次奖励静默丢失，
  日志只写一句「已上报但进度 0/1 未达成」。
- **修法**：改成「在截止时间前一直查」（`PROGRESS_POLL_TIMEOUT = 20.0`，
  间隔 2 秒），进度一到位就停。

### T-2　夜猫子任务每晚上报 3–4 次（HIGH）

- **现象**：调度器的 01:00 槽位**同时**跑 `run_night_growth` 与 `run_growth_tasks`。
  前者报 1 次夜间事件；后者在 `_progress_one` 里看到「现在是夜间窗口」
  ⇒ 再补报 `tgt - cur` 次。而上游的契约是**每天 1 次、累计 3 天**。
- **修法**：`run_growth_tasks(..., skip_night=True)` —— 夜间任务由夜间那条路独占。

### T-3　任务查询失败被静默吞掉（MEDIUM）

- **现象**：`fetch_growth_tasks` 吞掉**所有**异常且**不记日志**
  ⇒ 「上游改了接口」与「今天没有任务」在面板上完全一样（都是空列表），排查时只能靠猜。
- **修法**：按模块自己的 `set_logger` 契约记一笔日志
  （模块里其它查询 `fetch_growth_summary` / `fetch_streak_days` 都记了，只有这里漏了）。

## 五、正确性类

### C-1　上游恢复时刻没有上界（MEDIUM）

- **现象**：上游正文里的重置墙钟如果写的是「下个月恢复」，
  账号会被停放一个月 ⇒ 等于从池子里**静默消失**，面板只显示「无可用账号」。
- **修法**：`RATE_LIMIT_RESET_MAX_WAIT = 24 * 3600` 夹取上界；
  下界沿用原有的 `max(1.0, ...)`（上游时刻已经过去时不能立刻重新上线然后立刻再撞）。
- **回归网**：`tests/_test_rate_limit_clamp.py`（11 项）。

### C-2　`README.md` 的套件数堆了 16 行互相冲突的历史数字（MEDIUM）

- **现象**：每次发版**追加**一行而不是更新 ⇒ 209/211/226/227/228/229/231/232… 全在。
- **修法**：收敛为唯一正确的一行；此后每加测试文件同步更新
  （`tests/_test_release_engineering.py` 会断言 README 与树里实际数量一致）。

### C-3　损坏的 `settings.json` 被断言为「读出空 dict」（MEDIUM）

- **现象**：`_test_hotpath_savings.py` 里有一条用例断言
  「损坏文件 → `load()` 返回 `{}`」—— **它把漏洞本身固化成了契约**。
- **修法**：断言改为「读出来带 `_UNREADABLE` 标记」，
  并由 `tests/_test_settings_fail_closed.py` 覆盖新的（正确的）语义。

## 六、未修的（写明原因与影响）

| # | 问题 | 为什么不修 | 影响 |
|---|---|---|---|
| N-1 | 默认面板口令 `admin` | 它是**既有设计**（README 明写「首次登录后请立即改掉」），改成强制会在升级时把用户锁在面板外 | 真实风险在部署侧：面板密码必须在 `.env` 里设成随机强口令。审计建议的「非回环绑定 + 默认口令 ⇒ 拒绝启动」**未实施** —— 它会让忘记改密码的存量部署直接起不来 |
| N-2 | `GET /settings/reveal` 返回完整 API Key、`GET /accounts/export?secrets=1` 返回全部账号令牌 | 二者都只凭**面板会话**（API Key 不够），面板会话本身已是管理员权限 | 属「管理员可以导出凭据」的设计选择，不是越权。要收紧需引入二次口令 |
| N-3 | API Key 存在 `localStorage`（面板令牌在 `sessionStorage`） | 改存储位置会让「刷新页面免重新登录」这个体验消失 | 面板口令已不落 `localStorage`；API Key 是长期凭据，属可讨论的取舍 |
| N-4 | `?key=` 仍可从 query string 传 API Key | 改掉会破坏「一条链接直接接入」的用法（README 主推的用法） | 风险是 Key 会进访问日志/历史/Referer。已对 `?pwd=` 做了同样的清理 |
| N-5 | `/health` 与 `/panel/status` 无鉴权，泄露账号数、区域、是否仍是默认口令 | 监控脚本依赖它们 | 属有意暴露；`panel_password_is_default` 只对已登录的人显示更合适，未实施 |
| N-6 | CI 的 `uses:` 固定到 tag 而非 commit SHA | 改成 SHA 要维护一份更新列表 | 本项目 CI 不跑第三方 action，风险有限 |
| N-7 | `wb_webtools` 的 DNS 重绑定 TOCTOU | 要改成「解析后按 IP 直连 + 校验 Host/SNI」，改动面大 | `wb_webtools` 的解析失败已经是 fail closed，只剩重绑定这一个窄窗口 |
| N-8 | 三个「日界」不一致（宿主机本地时区 / 固定 +08:00 / UTC） | 统一要改四处语义，且会影响已有的用量统计口径 | 部署侧应统一设 `TZ`（compose 与 Dockerfile 已设；裸机启动脚本未设） |
| N-9 | 调度器槽位标记只在内存（重启丢当轮） | 要落盘，涉及状态文件与并发写 | 账号级的 `last_checkin` / `last_daily_chat` 是**持久化**的，
  重启后不会重复领奖 —— 丢的只是「某小时的槽位被评估过一次」，不是重复的上游动作 |
| N-10 | `wb_logstore` 的 `max_id()` 另开连接可能撞 `database is locked` | 要改成在 worker 连接上读 | 撞上时 id 计数会重启，`INSERT OR REPLACE` 可能覆盖旧行 |

## 八、方法论：这一轮学到了什么

1. **「新写的代码」最需要审计。** 本轮 4 个 HIGH 里，
   **3 个是我这一轮自己引入的**（D-1 死代码、D-6 泄漏、D-5 刷新放大），
   而它们都被「代码审查 agent + 实测复现」抓住了。
   ⇒ 自己写的代码不能因为「我刚写的」就免检。

2. **审计论断必须实测复核。** 审计报告给了 5 条论断（C1/H1/H2/H3/H4），
   我用探针逐条跑了一遍 —— **全部成立**。但其中一条（C1）的表述需要修正：
   它说「半开探测是死代码」，而我的第一版验证脚本测的是「一个账号冷却、其它健康」——
   按设计（健康优先）那种情况下**本就不该**触发探测。
   ⇒ 「探测没被触发」不等于「死代码」，要看场景。
   **真正的证据是：`_recovery_deadlines` 恒为空。**

3. **旧测试可能固化的是漏洞。** C-3 那条断言（「损坏文件 → 读出空 dict」）
   在它写下的那天是对的，但它把 S-1 这个 CRITICAL 变成了「有测试保护的行为」。
   ⇒ 改行为时要问一句：这条断言保护的是**意图**还是**当时的实现**。
