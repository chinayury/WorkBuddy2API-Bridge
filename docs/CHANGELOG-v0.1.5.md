# CHANGELOG v0.1.5

## 账号池告警通道：让网关自己开口（借鉴 P2-7 / P2-8）

v0.1.4 加了未验证账号护栏，挡住了坏号进池。但护栏只解决「**不让事故发生**」，
不解决「**发生了谁知道**」。

2026-10-26 晚到 10-27 凌晨那两次事故暴露的就是这一层：

| 时刻 | 事实 | 谁发现的 |
|---|---|---|
| 21:22 | 2 个零成功账号被重新启用 | 一次临时巡检脚本（**不是**网关） |
| 23:39 | 3 个正常账号被停用、3 个未验证账号被启用 | 同上 |

两次都**不是服务挂了，而是差一步**。而「差一步」之所以能持续将近半小时没人管，
是因为网关**一声不吭** —— 全树零告警通道（P2-7 / P2-8 的审计结论）。

本版补上这条通道。

### 一、做什么

新增 `wb_alerts.py`（借鉴 `misakano7545/workbuddy2api-panel` 的
`internal/alert/alert.go` 与 gitee `li-luoqiang/workbuddy-checkin`）：

- **HMAC-SHA256 签名的 webhook**（`X-WB2A-Signature` 头，十六进制）
- **ServerChan 推送**（`https://sctapi.ftqq.com/<key>.send`）
- **阈值型去抖**：可派发账号数低于阈值连续 N 轮 → 发故障；连续 M 轮恢复 → 发恢复

### 二、三条触发线

| 事件 | 触发点 | 去抖 | 为什么值得立刻通知 |
|---|---|---|---|
| `pool_degraded` | 调度器巡检循环 | 2/2 | 池子被做空了 —— 客户端马上会拿 429 |
| `restriction_wave` | `note_account_restriction()` | **不去抖** | 整池暂停，客户端**立刻**拿 429 |
| `unverified_rearmed` | 面板 `/accounts/set` 启用动作 | **不去抖** | 「谁在什么时候把什么装回来了」 |

第三条是本版最针对性的一条：**有人（或某个流程）启用了一个上游从未消费过的账号**
时立刻通知。2026-10-26 晚的两次事故都是这个动作引起的。

### 三、四条底线

1. **默认全关** —— 没配 webhook / ServerChan 时，本模块**不发任何网络请求**。
2. **不阻塞** —— 告警走后台守护线程 + 有界队列（200）；队列满就丢并计数，
   **绝不反压业务请求**。投递失败也只计数，不抛异常。
3. **去抖** —— 连续命中才算数。默认 2/2：单次抖动很常见，1/1 会让告警变成噪音，
   而告警一旦被无视就等于没有。
4. **secret 只写不读** —— webhook secret 与 ServerChan key **只存不显**：
   面板回读只有「配没配」两个布尔值，输入框留空即「保持原值」。
   `settings.json` 权限 0600（与 API Key 同一把锁）。

### 四、判据用「可派发」而不是「启用」

阈值判据用的是**可派发**账号数（`enabled` 且未被护栏隔离），不是启用数。
原因：v0.1.4 的护栏让 `enabled=True` 的账号也可能不参与派发，
只看启用数会**高估容量** —— 于是「池子其实已经空了」这件事看不出来。

### 六、过程中修掉的两个真实缺陷

**1. 去抖在抖动时会误发**（单测 `test_flicker_never_fires` 抓出）

第一版把「命中」与「未命中」**共用一个计数器**。于是「命中-未命中-命中」这种
抖动会把计数推过阈值，单次抖动就发一次故障通知。

改成**两个独立计数器**：中间只要断一次，计数就归零。「连续」这个词这才名副其实。

这条比看起来重要 —— 告警一旦变成噪音，运维就会开始无视它，那等于没有告警。

**2. 面板 JS 被我写坏**（43 个 JS 套件抓出）

新增 `saveAlerts()` 时插进了 `saveCreditsRefreshHours()` 的注释中间，
把那段块注释劈成两半 → 半个注释块里的中文变成裸文本 → `Invalid or unexpected token`。

**同一个错我今天犯第二次**（v0.1.4 那次是 `esc(...)` 多一个右括号）。
两次都被 JS 套件立刻抓住 —— 回归网有效，但这说明我在 dashboard 里动刀时
应该先跑一遍 `node --check`，而不是依赖全量回归才发现。

### 七、验证

- **新增单测** `tests/_test_alerts.py`（21 项断言）：配置读取、secret 不回读、
  去抖语义（含抖动不误发）、队列满即丢、投递失败不抛异常、签名与 body 匹配、
  settings 权限 0600。
- **回归**：`python tests/run_all.py --jobs 4` → **229 passed / 0 failed**
  （套件 228 → 229；README 的套件数断言同步更新）。
- **生产**：v0.1.4 上线 5 小时内**零 11140、零客户端 429、零账号启停变动**；
  护栏的三态在生产上自证 —— 4 个零消费账号持久化了 `unverifiedSince`，
  5 个账号因真实成功获得 `verifiedAt`（含 `f630e6c4` 在 05:11 通过验证），
  3 个「有上游消费但没经本网关派发过」的账号**未被误判**。

### 八、与借鉴清单的关系

本版落实 **P2-7（HMAC 签名 webhook + 去抖）** 与 **P2-8（ServerChan 推送）**，
两条都是审计里的「真缺口」，且审计明确指出：**P2-7 不能替代 P1-8 的预防作用，
但它决定「多久才发现」**。v0.1.4 已做预防，本版做发现。

其余借鉴点的状态见 `research/可借鉴要点清单.md` 第九节。
