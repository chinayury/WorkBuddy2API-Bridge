## 一、v0.1.0 的定位

上一版（2026-10-24 部署）实际上是**「官方镜像 + 4 个 bind-mount 覆盖文件」**：
补丁文件宿主机一份、容器里一份、两处内容靠人工同步。这套形态有三个结构性问题：

1. **上游一更新，被 bind-mount 的那几个文件不会跟着变** —— 表现为「升级了但那几个文件还是旧的」，
   新旧版本混跑极难排查；
2. **补丁源与线上不一致时无法察觉** —— 本次审计就发现本机 `deploy/` 里的补丁源比线上那份**更旧**，
   直接部署会把线上已有的修复退回去；
3. **没有版本号约束** —— 代码里的版本串是上游的 `1.7.33`，与本部署实际内容无关。

v0.1.0 把这三件事一起解决：

| 改造前 | v0.1.0 |
|---|---|
| 官方镜像 + 4 个 bind-mount 补丁 | **自包含源码树 + 本地构建镜像**，补丁是镜像的一层 |
| 补丁源与线上两份，靠人工同步 | **单一发布树** `release/`，本地与线上同源 |
| 版本串 = 上游的 `1.7.33` | **版本锁定 `0.1.0`**，两处版本串一致 + `VERSION` 文件 |
| 无发布级回归网 | **225 个上游套件 + 3 个本地补丁测试**，改动前必跑 |
| 改补丁无从判断会不会打破上游行为 | 每个本地测试都带**控制组**（拿纯净上游跑必须失败） |

## 二、新增功能

### 2.1 运行时凭据脱敏（`wb_proxy.py`）

新增 `register_secret()` / `_mask_secrets()` / `_register_pool_secrets()`，接入 `add_log_entry()` 与 `log()`。

- **登记运行期真实值**（账号 access/refresh token、面板 API Key），命中即打码 ——
  不靠正则去猜「什么长得像 token」，那种做法既会漏（形态千变万化）又会误伤（把错误码当密钥打码，日志失去排查价值）；
- **长值优先、一次替换**：短值常是长值的子串，先替短的那个会把长值切成两半，反而漏出后半段；
- **过短的值不登记**（< 12 字符）：账号 id、错误码片段都可能撞上，打码反而误导；
- 池子每时每刻都在变（token 会刷新），所以每次打码前扫一遍当前池 —— 几十次集合查找，开销可忽略，
  比「登记一次、之后漏更新」安全。

**为什么重要**：面板的 `/logs` 是任何能打开面板的人都能看的；原来只有手机号被掩码，
账号 token 一点打码都没有。

### 2.2 不可伪造任务显示「需人工」而不是「进行中」（`dashboard.html`）

上游把「已接取但进度没动」的任务一律渲染成「进行中」。对**可自动化**的任务这没错（引擎正在推进度），
但对 `wb_wechat_oa_subscribe_task`（上游标 `unforgeable: true`，需真人微信关注公众号满 24 小时）
就是误导 —— 看起来像卡住了，实际是等真人。

现在这类行渲染成琥珀色 **「需人工」** 徽章，并把 `reason` 直接写出来：
「需在微信关注「腾讯 WorkBuddy」公众号满 24 小时」。

**分支顺序特意排在「待领奖」之后**：真人做完之后上游会把它标成已达成，那时仍要正常显示「待领奖」+ 领取按钮。

### 2.3 导入支持多选并合并成一次提交（`dashboard.html`）

上游的文件选择器没有 `multiple`，一次只能选一个 `.json`，批量纳管账号要一个一个来。
现在可选多个文件，把各文件的账号行合并成**一次**原子提交（服务端 `/accounts/import` 接受裸数组），
并保留「先预览、再提交」的交互。

### 2.4 桌面端 / 网页端指纹事件链（`wb_tasks.py`）

上游把「需电脑端」的任务（`RichMeow_Chat` / `Library_read` / `Buddy_App` / `Buddy_App_QQ`）
硬编码进 `DESKTOP_ONLY_TASKS` 直接跳过 —— 那些行在面板上永远停在「进行中」。

本项目补上了两条事件链（移植自 `linguo2625469/workbuddy2api-panel` 的 `internal/upstream/desktop.go`）：

- **桌面端**：向 `copilot.tencent.com/v2/report` 上报 6 连事件（`agent_task_created` → `chat_message_send` →
  `chat_request_send` → `chat_message_response` → `chat_message_status` → `chat_request_response`），
  指纹形态对齐官方客户端；
- **网页端**：向 `www.workbuddy.cn/v2/report` 上报单条 `web_element_click`，
  带 `x-client-platform: web` 与浏览器 UA，用于页面行为类任务。

实测：单账号 7 个卡死任务全部由「accepted 0/1 → claimed 1/1」点亮。

### 2.5 专家 id 通用解析（`wb_tasks.py`）

上游的「体验某专家」任务（`expert_use_*`）不在已知任务表里 → 静默跳过 → 面板永远「进行中」。
现在从任务的 `jump_url` 里通用解析出专家 id（`expertId%3Dex_XXX`），走通用处理 ——
**上游新增专家任务不必改代码**。

### 2.6 每日 01:00 成长任务队列（`wb_scheduler.py`）

上游的成长任务积分只能靠面板的「一键做任务」按钮拿 —— 没人点就每天白丢几百积分（实测单账号约 500 分）。
现在调度器在每日 01:00 自动跑一轮完整闭环：接取 → 事件上报 → 领奖。

实测：18 个账号一轮 7 分钟，首次强制触发 +4100 积分；01:00 自动轮无人值守跑通（`last_run_time=01:00:21`）。

### 2.7 超大工具定义压缩（`wb_proxy.py`）

腾讯上游的 Kimi 系模型对**单个** function 定义有三重上限（实测）：

| 限制 | 放行 | 拒绝 |
|---|---|---|
| 单个 schema 体积 | ~125KB | ~130KB → `400 {"code":11133}` |
| 嵌套深度 | 25 | 30 |
| 单个字符串长度 | ~110K 字符 | ~120K 字符 |

典型触发源是 MCP：服务端把整份 JSON Schema 原样塞进 `parameters`
（例如 `mcp__rea__compare_web_captures` 有 180KB、3093 个 schema 节点、32 层嵌套，三条上限全踩），
结果是**每次 Kimi 调用都失败**，而 glm / step / minimax / mimo / deepseek 打同一份 payload 全部 200。

现在超过阈值的工具定义会被压扁：保留顶层属性名、类型与 `required`，更深的 object 只留 `{"type":"object"}`，
长字符串截断，丢掉上游校验器用不到的关键字。模型仍然知道这个工具有哪些参数、什么类型，
而定义从 180KB 降到几 KB。阈值可用 `WB_MAX_TOOL_DEFINITION_BYTES` 调整（默认 64KB）。

### 2.8 发布工程化（本次新增）

- **`release/` 自包含发布树**：纯净上游 + 补丁整合，不依赖 bind-mount；
- **225 个上游套件**跑通（`python tests/run_all.py`），作为改动前的回归基线；
- **3 个本地补丁测试**，每个都带控制组（拿纯净上游跑必须失败，否则测试不敏感）：
  - `test_task_patch.py` —— 任务引擎补丁，40+ 断言
  - `test_log_mask.py` —— 运行时凭据脱敏，15 断言
  - `test_multifile_import.js` —— 面板多选导入，13 断言
- **版本锁定**：`VERSION` 文件 + 两处版本串 + OpenWrt 打包号，统一为 `0.1.0`；
- **`docs/` 全套中文文档**（本目录 6 份）。

## 三、修复与重构

完整清单见 [BUGFIXES-v0.1.0.md](BUGFIXES-v0.1.0.md)。此处只列结构性改动：

| 改动 | 性质 | 说明 |
|---|---|---|
| **调度器单账号任务隔离** | 解耦 | 账号循环内 8 处任务调用原本全无 try/except，一个账号抛异常就打断整轮（后面所有账号都不跑）。现在每账号的任务块整体包一层，失败只记一行日志 |
| **出口判定单一事实源** | 重构 | `detect_model_realm()` 原本另有一份硬编码集合，与 `exclusive_realm()` 互相矛盾（`glm-5v-turbo` 因此完全不可达）。现在统一查表，删掉矛盾的那份 |
| **环境变量解析统一容错助手** | 重构 | `_env_int()` / `_env_float()` 提到文件前部，替换全部 8 处裸 `int()`/`float()`。裸解析会让一个手误的可选参数把整个网关卡在 import 阶段 |
| **帧清洗三路对齐** | 重构 | `clean_chunk` 补上 `tool_calls[].function.name` 过滤，与非流式的 `aggregate_stream` 对齐（此前同一对话在流式与非流式下给出的工具调用不一样） |
| **body 记账顺序** | 重构 | `_body_consumed` 的置位从「解码之后」提到「读完之后、解码之前」，消除「已读但标记未置 → 二次读永久阻塞」这一类缺陷 |

## 四、兼容性变化（升级须知）

v0.1.0 有 4 处**行为变化**，升级前请确认调用方不受影响：

| # | 变化 | 影响 | 迁回方式 |
|---|---|---|---|
| C1 | `GET /accounts/export` **默认不再导出明文凭据** | 任何依赖导出文件里带 token 的脚本会拿不到凭据 | 请求时显式加 `?secrets=1` |
| C2 | `/realm` 纳入面板路由白名单 | 只有 API Key（无面板会话）的调用方不再能切出口 | 用面板会话调用；或按需回退该行 |
| C3 | 启动横幅不再打印明文 API Key | 依赖 stdout 抓 Key 的自动化脚本会失效 | 从 `accounts/settings.json` 读（权限 0600） |
| C4 | **模型出口判定改变** | `glm-5v-turbo` 从「完全不可达」变为正确路由到国内出口；`minimax-*` 不再被前缀一刀切钉到国内出口 | 若某部署确实只有一个出口、依赖旧的「全部 minimax 走 cn」行为，需自行加回 `CN_EXCLUSIVE_PREFIXES` |

> C4 是**修复**而非收紧：旧行为会让「只有国际账号」的部署请求 `minimax-*` 直接失败，且跨出口兜底是单向禁用的，救不回来。

## 五、版本迭代说明（路线图）

v0.1.0 是**稳定基线**，不是终点。下一版（v0.2.0）建议按以下顺序推进，
每条都对应 BUGFIXES 附录里的编号：

### v0.2.0 建议范围

1. **A1 前后端字段契约**（面板 Key 的 `concurrency_limit`）——
   后端 `runtime_settings_view()` 补字段，前端未编辑时不提交该键；加一条「前端消费字段 ⊆ 后端返回字段」的契约测试。
   这是**唯一一条已确认会让用户数据被静默清零**的问题。
2. **A8 鉴权统一为「默认拒绝 + 显式声明信任等级」的单点判定表** ——
   现在的 `_is_panel_route` 白名单 + 逐路由自查 `_panel_ok()` 是两套并行判定，四档信任语义交叉，
   已经产生过两处「当前靠别处兜住」的越权风险。
3. **A6 面板长耗时动作后台化 + 幂等锁** —— 一键跑任务 / 一键测试现在同步占用请求线程且可并发重复触发。
4. **A5 按 API Key 维度的用量聚合** —— 多人共用网关时「哪个 Key 花了多少钱」目前答不出来。
5. **A4 出口判定的第三份事实源** —— `wb_catalog` 的目录快照与 `exclusive_realm()` 仍是两张表。
6. **A2/A3/A7 三项大重构**（`open_upstream` 拆分、帧清洗收敛为单一权威实现、`_handle_settings_save` 表驱动）
   —— 风险最高、收益最长，建议在 1~5 完成、回归网成熟后单独排期。

### 明确不做

| 项 | 原因 |
|---|---|
| 升级到官方 v1.8.0 | 上游已到 `4f7ae6f`（比本基线多 955 次提交），但本项目的补丁是按 `d1a8913` rebase 的。换基线 = 逐条 rebase 补丁 + 全量回归 + 上游行为变更的重新评估，是独立一轮工程，不应与 v0.1.0 的稳定化混在一起 |
| 引入第三方依赖 | 当前零依赖是最大结构性安全优势（见安全审查报告第二节），不值得为便利性放弃 |
| 拆分 `wb_proxy.py`（23k 行） | 风险高于收益；本版只做了「事实源统一」与「异常隔离」两处低风险收敛，真正的拆分留给有充分回归网之后 |

## 六、版本谱系

```
上游 ardeyouxianyi/workbuddy2api-hub
  v1.7.33  ──► 本地补丁层（bind-mount 形态）  ← 2026-10-24 部署的上一版
  d1a8913 ──► 本地补丁层（整合进源码树）
                    │
                    └─► v0.1.0  ← 自包含发布树 + 镜像化部署 + 回归网 + 版本锁定
```

| 版本 | 含义 |
|---|---|
| `1.7.33` | 上游版本。本项目 v0.1.0 的**代码基线**是 `d1a8913`（2026-10-24），与 `1.7.33` 同代但含后续修复 |
| `0.1.0` | **本项目**的发布版本号。语义：本项目自身的第一个稳定版，与上游版本号独立 |

上游版本号的来源与约束见上游 `.github/workflows/tests.yml` 的 `version-assert` 任务：
源码里的两处版本串必须一致，且 release tag 必须等于源码版本。v0.1.0 沿用同一约束
（`wb_proxy.py` 的 overview `"version"` 与 `server_version` 均为 `0.1.0`）。
