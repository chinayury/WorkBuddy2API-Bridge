## 二、账号管理（v0.1.0 的行为变化在这页最明显）

### 2.1 「为什么这个号不出现在选号里」

面板的「网关与账号」页会直接写明原因（判定顺序与内部一致）：

| 面板上的说法 | 含义 |
|---|---|
| 已停用 | `enabled=False`，不参与派发 |
| 无凭证 | 没有 accessToken |
| 凭证已过期 | 上游明确拒绝了这个凭据 |
| 该模型已被人工禁用 | 面板上把这个模型拉黑了 |
| 该模型仅限 PRO 账号 | 账号不是付费档 |
| 软限流冷却 / 熔断 / 降权 / 余额保护 / 上游风控限制 | 各自的到期倒计时 |
| **未验证**（红色徽章） | 上游从未消费过这个凭据，**已隔离**（见下） |

### 2.2 未验证账号护栏（重要，会影响你的池子）

**一个从未被上游真正消费过的凭据，第一次派发就会被上游判 403 / 11140**，
而 900 秒内两次就触发整池 30 分钟连坐暂停（客户端全拿 429）。

⇒ 护栏在**派发之前**就把它隔离了：面板显示「未验证」红色徽章，
这个号不会接到任何真实流量。

**它怎么被解除**：一次真实成功（成功服务过、或探针拿到过上游应答）。
**注意**：上游额度快照显示 `used == 0` 但你**确实**用它成功过 —— 那就说明
「上游接受过它」，护栏会自动放行（`verifiedAt` 字段持久化，重启也不丢）。

> **别手动启用「未验证」账号**。它就是事故的源头。
> 要用它，先在面板上点「测试」确认能通。

### 2.3 在途感知（v0.1.0 新增，你可能感觉到的变化）

以前：并发请求会自发收敛到同一个账号（池子的偏好全是静态的）。
现在：网关会看**当前谁在忙**，把请求分摊给闲的账号。

**你可能观察到的现象**：面板上各账号的请求分布比以前均匀了；
某一个号不再是「什么都往它身上压」。

**为什么重要**：上游按「账号 + 分钟」计 token，
两个会话落在同一账号上很容易冲破配额然后 429；
换号之后又因为丢了前缀缓存而更慢（首字延迟 1.5s → 5~6s）。

**它与「每账号并发上限」是两件事**：
- **在途感知**永远开着，只影响**给谁**；
- **每账号并发上限**（设置 → 账号限额）是硬上限，默认 0 = 不限。

### 2.4 半开探测（v0.1.0 新增）

**冷却刚到期的账号不会立刻接单** —— 只放一个请求去试探，
其余请求改选别的账号。试探成功它才恢复常态。

**你可能观察到的现象**：某个号刚过冷却期时，面板上它的请求数会慢一拍才开始涨。
这是**有意**的：冷却一到期就全员压上，很容易再撞一次。

## 三、任务与福利

### 3.1 每日自动化槽位

| 时间 | 做什么 |
|---|---|
| 09:00 / 21:00 | 国内版签到、活跃上报、猫猫旅行（09:00 派出 / 21:00 领奖）、连登档位兑换 |
| 01:00 | 夜猫子任务、成长任务队列 |
| 22:00 | Token 保活（令牌快到期时提前刷新） |

### 3.2 哪些能自动、哪些不能

| 能自动 | 不能自动（会诚实跳过并给出原因） |
|---|---|
| 签到、连续打卡、猫猫旅行、连登兑换、抽奖 | **公众号关注**（需真人微信关注满 24 小时） |
| 成长任务（桌面/浏览器指纹事件链） | **真实捐款**类任务 |
| 积分刷新 | 未知的新任务（会说明「不在已知任务表里」） |

### 3.3 v0.1.0 的两个变化

**夜猫子每晚只上报一次**（以前 3~4 次，上游契约是每天 1 次、累计 3 天）。
多余的次数要么被上游忽略，要么让进度算错。

**任务进度等待从 3 秒延长到 20 秒**。以前实际只等 3.0 秒，
而实测落账要 3~4 秒 ⇒ **一半任务当天领不到奖**，顺延到明天静默丢失。
现在等到进度落账为止。一轮任务会多花几秒。

### 3.4 任务的幂等与「0 积分」

| 现象 | 含义 |
|---|---|
| 成长队列 +0 积分 | **正常终态** —— 上游的成长任务多为一次性，领过一次就不再刷新 |
| 签到显示 0 个 | 你今天已经手动签过了（`can_checkin` 返回 False），不是故障 |
| 夜猫子提示「未获取到任务清单」 | 上游现状，不是故障 |
| 剩 18 条 `wb_wechat_oa_subscribe_task` | 需真人微信关注满 24 小时，**正常终态，别再「修」** |

## 四、用量与计费

**积分口径**：`credits.remain` 求和（可用余额）。

**成本估算**：基于 OpenRouter 的等价 token 花费（不是上游账单），
USD 按 7.10 换算成 CNY，可在 `pricing-markup.json` 里加价。
**未定价的模型会被报告出来，不会被静默算成 0。**

**上游错误正文里的凭据不再落盘**（v0.1.0 加固）：
失败行的 message 已按已知凭证形态脱敏（`Authorization: [redacted]`），
`usage/usage.jsonl` 权限收紧到 0600。

## 五、设置项

### 5.1 账号限额

| 项 | 默认 | 说明 |
|---|---|---|
| 每账号并发上限 | 0（不限） | 硬上限。默认不限是为了与上游行为一致 |
| 每日 Token 配额 | 0（不限） | 按区域生效 |
| 每日积分消耗 | 0（不限） | 按区域生效；免费模型不受这个限制 |
| 单模型每日 Token | 0（不限） | 只有一个模型被挡住，账号照常服务其它模型 |
| 积分保留线 | 0 | 低于此值不再派发（避免触发上游的余额提醒短信） |
| 临期积分窗口 | 0 | 窗口内的账号优先被派发（让快过期的先花掉） |

### 5.2 账号池告警

| 项 | 默认 | 说明 |
|---|---|---|
| Webhook URL | — | **必须是公网地址**；指向内网/回环/元数据地址会被拒绝（保护） |
| 签名 Secret | — | 留空则**不签名**投递 |
| ServerChan Key | — | |
| 可派发账号阈值 | 8 | 低于它算降级 |
| 连续轮数 | 2 | 连续命中才算数（单次抖动不告警） |

**触发线**：

| 事件 | 触发点 | 去抖 |
|---|---|---|
| 账号池降级 | 调度器巡检循环 | 2/2 |
| 风控连坐 | 账号被判风控时 | **不去抖**（整池暂停，客户端立刻拿 429） |
| 未验证账号被启用 | 面板启用动作 | **不去抖**（谁在什么时候装回了炸弹） |

> **DNS 抖动时告警发不出去是设计如此** —— 解析失败一律拒绝（fail closed）。
> 收不到告警比被 SSRF 打穿好得多。

## 七、排查手册

### 7.1 池子空了

1. 面板「网关与账号」页看每个号的**拒绝原因**（表格在 §2.1）；
2. `/health` 看 `accounts` / `accounts_ready`；
3. 「运行日志」页搜 `cooling` / `restricted` / `unverified`。

### 7.2 客户端一直 429

- 上游按「账号+分钟」计 token ⇒ 上下文太长 + 并发高就会撞；
- **开新会话**（既降上下文，也降额度消耗速度）；
- 调低 `WB_MAX_CONCURRENT_CHAT`；
- 看有没有账号在**风控连坐**（整池暂停）。

### 7.3 agent 卡在「思考中」

这是**流式工具调用**的形状问题，客户端侧会报 `Tool Not Found`。
v0.1.0 的金丝雀固件（`tests/fixtures/upstream_sse/`）就是为守住这块而存在的。

### 7.4 某个号一直不出现在选号里

按 §2.1 的表格逐条对；
注意「未验证」这一档 —— 它挡的是**派发**，不改 `enabled`，
所以面板上可能显示「启用」但它从不被选中。
