# CHANGELOG v0.1.4

## 未验证账号护栏：把「上游可能判非法的凭据」挡在派发池外

v0.1.3 把池子治理成了「10 个启用（全部已验证可服务）+ 9 个停用」。但那一版治理是
**人工做的**——靠运维脚本逐个账号判定，而**护栏本身不存在**：任何一个账号，只要在
面板上被点一下「启用」，它就会重新进池派发。

2026-10-26 晚到 2026-10-27 凌晨，这一条被现实验证了**两次**。

### 一、事故复盘

**第一次（2026-10-26 21:22–21:23）**：`POST /accounts/set` 连续 5 次，把 20:41 刚
停用的那批账号里的 `e73f2aeb` 与 `fd5ba0df` 重新启用。就绪数从 10 跳到 12。
两者都是「网关侧成功次数 = 0」的账号，且 `fd5ba0df` 的 `weight=2` 会让它进入
**最高优先级派发层**（`wb_accounts.py` 的 `_pick_weighted_first`）——不是边缘化，是
优先。同一时刻 `725247b7` 因 kimi-k3-1 配额耗尽进入模型冷却，会话绑定松动、开始
轮转：**下一个轮到它们就可能引爆**。幸而未引爆（当轮流量未及），21:39 人工止损。

**第二次（2026-10-27 00:17–00:19）**：同样的模式再来一次，而且**方向完全反了**。
23:39–23:44 的操作停用了三个**正常账号**——`292b43a8`（成功 410 次）、
`0472cc9f`、`6d3fa971`（成功 104 次）——却启用了 `fd5ba0df`、`f630e6c4`、
**`f7102b2e`**。`f7102b2e` 是 `used == 0` 的账号，**零消费、零成功记录**，正是
11140 的目标。它在池子里待了约 30 分钟，幸而 `weight=5` 排位靠后、流量没轮到。

两次都不是「服务挂了」，而是**差一步**。

### 二、根因：判据错了，而且护栏不存在

**判据一（错的）**：`usage.jsonl` 里 `completed` 次数 = 0，即「网关侧从未成功服务过」。

这条判据**误伤**。它把 5 个「有上游消费历史、只是没经本网关派发过」的号也算成炸弹
（`e73f2aeb` / `f45878a9` / `f630e6c4` / `f7102b2e` / `fd5ba0df`）。实测：19 个账号里
「网关零成功」有 9 个，其中被 11140 的只有 4 个——**漏判 5 个、误判 5 个**。

**判据二（对的）**：上游额度快照的 `credits.used == 0`，即**这个凭据从未被上游消费过**。
实测分离度是**完美的**：

| 判据 | 命中 11140 | 漏判 |
|---|---|---|
| `credits.used == 0` | 4/4（100%） | 0 |
| 网关侧成功次数 = 0 | 4/9（44%） | 5 |

`used == 0` 的 5 个账号里 4 个已被上游 403 / 11140 判非法；`used > 0` 的 14 个账号里
**零个**被判过 11140。

**根因（更重要）**：以上都只是「怎么识别」。真正的问题是**账号池里根本没有「这个号
能不能用」的概念**——`ready()` 只看 enabled / 凭据 / 冷却 / 额度 / 模型限制，
不看「上游接不接受这个凭据」。所以无论运维怎么判断，出错时池子都会照单全收。

这正是借鉴清单 **P1-8「凭据三态预验证」**要解决的问题，也是本次审计里
**16 条中唯一能从源头阻止坏号进池**的一条。

### 三、改法

#### 1. 三态，与上游应答一一对应

借鉴 `CangShui/workbuddy-gateway` 的 `credverify.go` 三态契约：**「明确拒绝」与
「无法判定」必须分开**，否则一次网络抖动就会误杀还能用的号。

| 上游应答 | 含义 | 网关动作 |
|---|---|---|
| HTTP 403 / code 11140 | 上游判非法 | `rejected` → 隔离，不参与派发 |
| HTTP 429 / code 14003「too many requests」 | **凭据被接受**，只是限流 | `verified` → 解除隔离 |
| 跑成一次 | 凭据被接受 | `verified` → 解除隔离 |
| `credits.used == 0` 且从未验证过 | 可能尚未被上游激活 | `pending` → 隔离，等待验证 |

14003 这一条是实测得来的（2026-10-27 00:19）：对两个从未经本网关派发过的账号各打
**一个**最小请求，得到的正是 `429 code 14003`（带 `retry_after: 13`）而不是 11140
——**它们的凭据被上游接受了，只是刚被限流**。若不区分这两者，这两个号会被永远
隔离在池子外，而它们其实只是等窗口过去就能正常服务。

#### 2. 落点

**`wb_accounts.py`**

- `Account` 新增三个持久化字段：`unverifiedSince` / `unverifiedReason` / `verifiedAt`。
  随凭据档落盘（**不进 `RUNTIME_ONLY_FIELDS`**）——判定是**上游事实**，重启后仍成立。
  否则一个没验证过的凭据会在每次重启后又被派发一次、再吃一次 11140。
- `Account.upstream_never_consumed()`：读额度快照的 `used == 0`。
  **额度快照缺失时返回 False** —— 拿不到证据不等于有罪，宁可放过也不误伤。
- `Account.ready()`：**在最前面**拦截未验证账号。语义上它挡的是「这个号根本不该
  接单」，优先于所有「暂时不可用」的判断 —— 一个被隔离的号不该因为冷却到期或
  额度刷新就漏进派发池。
- `Account.note_restricted()`：上游判非法时打标。**这是连坐循环的断点** —— 原来
  2 小时冷却一过它就重新进池、再吃一次 11140、再触发一次整池连坐。
- `Account.note_success()`：一次真实成功解除标记。
- `AccountPool.apply_unverified_guard()`：加载时按 `used == 0` 给存量账号打标。
  **只打标、不改 `enabled`** —— 护栏拦的是「派发」不是「状态」，面板显示与磁盘
  保持一致。

**`wb_proxy.py`**

- 真实流量的 429 分支：软限流（含 14003）即**解除**未验证标记 —— 上游回 429
  而不是 403，说明凭据被接受。
- `probe_account()`：403/11140 → 保持隔离并标 `rejected`；429/14003 → 解除隔离。
  探针成功路径本来就调 `note_success()`，标记自动清除。
- `/health` 新增 `accounts_unverified` 与 `accounts_upstream_unused` 两个计数。

**`dashboard.html`**

- 账号状态徽章新增「未验证」（红色），排在「可用」之前 —— 否则会被画成绿色而
  实际不接单。
- 「当前禁用」清单新增「未验证」条目，带原因文案。

#### 3. 一个真实的死锁（被单测抓出来）

第一版实现里，`mark_verified()` 只把「未验证」标记清掉。可上游额度快照的 `used`
不保证立刻更新 —— **一个刚验证通过的号，其 `used` 可能仍是 0**。于是重启后
`apply_unverified_guard()` 会把它重新隔离：**一个永远锁在池子外的死锁**。

修法：新增 `verifiedAt` 字段，**把「上游接受过它」这个事实本身持久化**。
`upstream_never_consumed()` 遇到 `verifiedAt > 0` 一律返回 False。

这是本轮新增的 17 项单测里被抓出来的一个真实缺陷（见
`tests/_test_unverified_guard.py::test_pool_does_not_re_mark_an_already_verified_account`）。

### 四、验证

- **单测**：新增 `tests/_test_unverified_guard.py`，17 项断言 —— 判定、拦截、
  解除、持久化、池级打标、以及上面那个死锁的回归。
- **回归**：`python tests/run_all.py --jobs 4` → **228 passed / 0 failed**
  （套件 227 → 228，README 的套件数断言同步更新）。
- **生产取证**：判据在生产 19 个账号上做了分离度检验（4/4 命中、0/14 误判）；
  两个未知账号各打一个最小请求，确认判据三态与实测一致。
- **池子修复**：按新判据处置 —— 停用 `f7102b2e`（`used == 0` 且已启用），
  恢复 `292b43a8` / `0472cc9f` / `6d3fa971`（被误停的正常账号）。
  处置后 12 个启用账号**全部 `used > 0`**。

### 五、边界与不做的事

- **护栏不改 `enabled`**：面板显示与磁盘永远一致；「停用 / 启用」仍是运维的
  决定权，护栏只决定「派不派它」。
- **不打探针**：护栏不主动向上游发请求。理由是探针本身会消耗配额、且可能触发
  11140 —— 本次审计已确认「验收探针可能把服务打进不可用状态」。验证动作由
  运维在面板上点「测试」触发，一次一个。
- **额度快照缺失不隔离**：`credits` 为空或 `used` 不可解析时返回 False。
- **导入的账号不自动隔离**：`apply_unverified_guard()` 只按上游事实打标，
  新导入且没有额度快照的账号不受影响。

### 六、与借鉴清单的关系

「16 条中唯一能从源头阻止坏号进池」的一条，且「能预防本次事故」。

其余 15 条的状态见 `research/可借鉴要点清单.md` 第八节（审计逐条核验结果：

但未改动 —— 它们涉及请求热路径与账号池熔断核心，风险最高的一档，需要单独一轮
带回归网的工程。
